# Kubernetes deployment

This path uses the same image and CLI as Railway. The [generic example manifest](../deploy/kubernetes.yaml) contains no credentials or cluster-specific Secret definitions. Replace its placeholders and create the referenced Secret privately before using it in your own staging namespace.

## Required configuration

Use a digest-pinned image, PostgreSQL, and S3-compatible object storage. Create the `sinopebase-runtime` Secret outside this repository with environment variable keys `POSTGRES_URL`, `JWT_SECRET`, `SINOPEBASE_SERVICE_ROLE_KEY`, `SINOPEBASE_ANON_KEY`, `S3_ENDPOINT`, `S3_ACCESS_KEY`, and `S3_SECRET_KEY`. The manifest references the Secret by name and contains no values. Keys and JWT secret must be the same on every pod. Set `BETTER_AUTH_URL` and `SINOPEBASE_EXTRA_ORIGINS` to the public HTTPS origin.

`S3_ENDPOINT` accepts `https://host` (port 443), `http://host` (port 80), or a bare `host[:port]` (default 9000). Use the storage provider's HTTPS origin, including an explicit port if needed. The same parser handles the application store and migration bucket. If SQL migrations live in S3, set `MIGRATIONS_BUCKET` and optionally `MIGRATIONS_PREFIX` on every pod. Confirm the credentials can list that bucket and the application buckets.

Set `SINOPEBASE_MULTI_REPLICA=true` and `SINOPEBASE_PG_NOTIFY=true`. Startup then requires PostgreSQL, S3, a shared ingress rate limit assertion, and no local OAuth provider file. PostgreSQL advisory locking serializes system and application migrations across pods. Each pod uses a pool of up to 10 PostgreSQL connections; one is held during migrations and one is held by the notification listener. Reserve database capacity for all pods and rollout surge. `/api/health` is liveness; `/api/ready` checks a database query and the notification listener. Route traffic only to ready pods.

Migration SQL and its ledger writes run in one transaction on the connection holding the advisory lock. If that connection fails, PostgreSQL rolls the transaction back and the pod fails startup. Migration scripts must use transaction-compatible SQL and must not commit the transaction themselves. The example pod uses `fsGroup: 10001` so its non-root process can write temporary files under the mounted `/data` volume.

Configure your ingress to **overwrite** incoming `X-Forwarded-For` and `X-Real-IP`, preserve the public Host and HTTPS scheme, and allow WebSocket upgrade on `/realtime/v1/websocket`. Set `TRUSTED_PROXIES` to your trusted ingress identifier only after verifying that behavior. This option enables use of the rightmost forwarded IP; the app cannot authenticate the TCP peer itself. Configure one shared ingress or edge rate limit for API and function traffic before setting `SINOPEBASE_EXTERNAL_RATE_LIMIT=true` in the manifest. The example leaves this `false`, so multi-replica startup fails closed until that protection is configured. The in-process limits remain per pod, so they are additional protection and do not define a fleet-wide quota.

OAuth providers must be identical on all pods. Set `SINOPEBASE_OAUTH_PROVIDERS_JSON` from a Kubernetes Secret containing an array such as `[{"providerId":"google","clientId":"…","clientSecret":"…"}]`, or bake the same code configuration into every replica. Roll all pods after a change. Multi-replica mode rejects a local `oauth_providers.json` file and disables Admin UI OAuth mutations. Function management routes are disabled too; supply the same read-only function files to all pods through the image or an immutable shared mount, then roll pods to publish changes. The base image has an empty `/app/functions`; mount files there if functions are needed.

Realtime row changes use PostgreSQL `LISTEN/NOTIFY`. A startup migration installs the notification function, and each pod attaches triggers to existing public user tables. Tables created after a pod has started need a rollout to attach triggers. PostgreSQL notifications are transient; changes committed while a listener is disconnected are not replayed. Notifications exceeding 7900 bytes are skipped so large writes still succeed. Presence, client broadcasts, and WebSocket message counters remain process-local. Do not rely on global presence or exactly-once broadcast delivery across pods. Use the database for durable events. Local settings mutations, backups, restores, and in-process scheduled backups are unavailable in multi-replica mode; use an external backup job.

## Verification before deployment

1. Build and release the image, recording its immutable registry digest and source commit. Pin the manifest to that digest.
2. Install the manifest in staging with two replicas and check both `/api/ready` endpoints and rollout status. Confirm only one pod applies a new migration and the second skips it.
3. Connect WebSocket clients through both pods, write a row through each pod and directly in PostgreSQL, and confirm both clients see each committed change once. Restart PostgreSQL or interrupt the connection and confirm readiness drops, reconnects, and recovers.
4. Upload and download an object through different pods using your HTTPS S3 endpoint. Test migration bucket listing if configured. Verify the ingress strips client-supplied forwarding headers and enforces a fleet-wide rate limit.
5. Test OAuth with an identical provider Secret on each pod if OAuth is used. Confirm file management routes are unavailable and function execution uses the same files on both pods.

The CI workflow provisions PostgreSQL and RustFS for integration tests. In-memory tests cover migration locking and notification listener failure paths; PostgreSQL integration tests exercise the advisory lock and notification migration. Configuration tests cover enabled and disabled deployment flags. CI validates the generic manifest with Kubeconform against Kubernetes schemas. Cluster-specific rollout and storage checks belong to the operator's private deployment process after the Kubernetes release.
